## Context

Hoje só `clientes` existe no banco: `id uuid primary key`, gerado na aplicação com `Guid.CreateVersion7()` (decisão do
design arquivado de `adicionar-clientes`, agora substituída). Não há nenhuma chave estrangeira. Os scripts DbUp já
aplicados (`0000`, `0001`) não podem ser editados. Produtos, pedidos e relatórios ainda não foram implementados; seus
artefatos de planejamento assumem `uuid` e a numeração `0002`/`0003`.

## Goals / Non-Goals

**Goals:**
- `id integer` gerado pelo banco em toda tabela; relações por `<entidade>_id integer` com chave estrangeira.
- Converter `clientes` sem perder dados e chegar ao mesmo esquema que um banco novo teria.
- Deixar as fatias seguintes já planejadas no novo padrão.

**Non-Goals:**
- Id público separado do id interno (descartado pelo usuário: o mesmo inteiro aparece na API).
- `bigint`: o pedido foi `int`; a troca futura seria outra migração.
- Reescrever designs de changes já arquivadas: ficam como histórico; esta change registra a substituição.

## Decisions

- **`integer GENERATED ALWAYS AS IDENTITY`.** Padrão SQL, sem sequência manual (`serial`), e `ALWAYS` impede que a
  aplicação informe o id por engano. Alternativa descartada: `GENERATED BY DEFAULT` — aceitaria ids vindos da aplicação
  e permitiria colisão com a sequência.
- **Id devolvido pelo `INSERT`.** `INSERT ... RETURNING id` numa única ida ao banco. A entidade nasce com `Id = 0`
  (ainda não persistida) e `IClienteRepository.InserirAsync` devolve o `Cliente` persistido, reconstruído com
  `Cliente.Restaurar` usando o id gerado. A entidade não ganha setter público de `Id`.
  Alternativa descartada: inserir e depois consultar pelo e-mail — duas idas ao banco e dependência de uma chave natural.
- **Conversão de `clientes` recriando a tabela (`0002_clientes_id_inteiro.sql`).** Numa transação (o DbUp usa uma por script):
  1. cria `clientes_novo` com o esquema final (`id integer generated always as identity primary key`, demais colunas iguais);
  2. `INSERT INTO clientes_novo (nome, email, criado_em) SELECT nome, email, criado_em FROM clientes ORDER BY criado_em, id`,
     para que os ids sigam a ordem de cadastro;
  3. remove `clientes`, renomeia `clientes_novo` para `clientes` e recria `ux_clientes_email` em `lower(email)`;
  4. renomeia a constraint de chave primária para `clientes_pkey`.
  Resultado: colunas na mesma ordem e com os mesmos nomes que uma criação direta. Alternativa descartada:
  `ALTER TABLE ... ADD COLUMN id integer GENERATED ...` na tabela existente — a coluna fica no fim da tabela e os ids
  seguem a ordem física das linhas, não a de cadastro. Recriar é seguro porque ainda não há chaves estrangeiras.
- **Renumeração das migrações planejadas.** `0002` passa a ser a conversão; `adicionar-produtos` usa
  `0003_criar_produtos` e `adicionar-pedidos` usa `0004_criar_pedidos`, com `cliente_id`, `pedido_id` e `produto_id`
  `integer` referenciando os `id` correspondentes. `adicionar-relatorios` não cria tabelas.
- **Id na API.** `int` em entradas, saídas, requests e responses; rotas `clientes/{id}` com `Id` `int` no request. O
  FastEndpoints rejeita valores não inteiros no binding da rota, e a resposta sai pelo formato padrão de validação
  (`400` com `errors.id`). Os testes que usavam `Guid.NewGuid()` para "inexistente" passam a usar um inteiro alto.
- **Convenção do projeto.** `openspec/project.md` troca "chaves `uuid`" por "chaves `integer` autoincrementais
  (identity) e relações por `<entidade>_id`".

## Risks / Trade-offs

- [Ids sequenciais são previsíveis] → todo `/api/v1` exige JWT e há um único usuário; nenhuma autorização por recurso
  depende de o id ser secreto.
- [Quebra do contrato: `id` de string para número] → marcado como BREAKING; README e `requests.http` atualizados.
- [Limite de ~2,1 bilhões de linhas por tabela] → muito acima do volume desta API; documentado.
- [Recriar a tabela exige lock exclusivo durante a migração] → aceitável no tamanho atual (ambiente de desenvolvimento);
  com chaves estrangeiras futuras o mesmo método exigiria recriá-las também.

## Migration Plan

1. Aplicar esta change antes de `adicionar-produtos`.
2. No startup, o DbUp aplica `0002_clientes_id_inteiro.sql` sobre bancos existentes (convertendo) e sobre bancos novos
   (logo após `0001`); os dois caminhos terminam no mesmo esquema.
3. Clientes da API passam a usar ids numéricos; ids UUID antigos deixam de existir.
4. Volta atrás: só com nova migração (o DbUp não desfaz scripts); os UUIDs antigos não são recuperáveis após a conversão.
